# Clean Water — техническое задание v1

Результат грилинг-сессии по [prompt.md](prompt.md). Документ фиксирует решения, принятые в трёх раундах интервью, и явно отмечает, что изменилось относительно исходной идеи.

---

## 1. Что строим

Платформа продажи осмос-фильтров и картриджей с автоматическими напоминаниями о замене.

**Две поверхности, одна кодовая база:**
- **Telegram Mini App** — основной канал. Авторизация по `initData`, клиент опознаётся по Telegram ID.
- **Публичный сайт** — тот же каталог в браузере, индексируется поисковиками. Вход через Telegram Login Widget; заявку можно оставить и без входа, по номеру телефона.

**Стек:** Next.js (SSR — нужен для SEO) + PostgreSQL + Prisma, всё в Docker.
**Хостинг:** Узбекистан (требование локализации персональных данных граждан РУз).
**Языки:** узбекский (латиница) + русский.
**Оплата:** нет. Заказ = заявка, менеджеру приходит уведомление в Telegram.

## 2. Скоуп первого запуска

### Входит в MVP

| Блок | Содержание |
|---|---|
| Каталог фильтров | Карточки с фото, характеристиками, ценой, видеообзором и обзорным текстом |
| Заявка | Кнопка «Заказать» → запись в базу + уведомление менеджеру в Telegram |
| Каталог картриджей | Расходники с указанием совместимости и ресурса |
| «Мой фильтр» | Личный экран: установленный аппарат, картриджи, шкала остатка ресурса, кнопка заказа замены |
| Автонапоминания | Telegram-сообщение при приближении срока замены каждого картриджа |
| Админка | Товары, редактор описаний, заявки, клиенты, отметки установки и замены |

### Не входит в MVP (второй этап)

- Квиз подбора фильтра
- Сервис-центр («о нас / услуги / цены / жалобы»)
- Отзывы клиентов
- Онлайн-оплата и рассрочка

Нереализованные пункты **не показываются** в меню — никаких заглушек «скоро».

## 3. Изменения относительно исходной спеки

Каждый пункт — сознательное решение, а не упущение.

| Было в prompt.md | Стало | Почему |
|---|---|---|
| Кнопка «выход из платформы» | Удалена | В Mini App пользователь всегда идентифицирован Telegram, выходить не из чего |
| Презентация загружается HTML-файлом | Визуальный редактор блоков с санитизацией | Загрузка произвольного HTML — это XSS-дыра, прямо противоречащая требованию защиты от injection |
| Прогресс-шкалы «заполняются сами» | Переназначены на реальные данные | Шкала показывает остаточный ресурс картриджа клиента и ступени очистки в карточке товара. Декоративный прогресс воспринимается как поломка |
| «Каждые 6 месяцев» | График по каждому картриджу | Механика/уголь ≈ 6 мес., мембрана ≈ 1.5–3 года, постфильтр ≈ 12 мес. Единый таймер слал бы неверные напоминания |
| «Bo'lib to'lash» (рассрочка) | Вне MVP, обсуждается менеджером вручную | Настоящая рассрочка — договор, скоринг, паспортные данные, интеграция с Uzum/Alif. Отдельный крупный этап |
| PostgreSQL «или» MongoDB | PostgreSQL | Данные строго реляционные: клиент → аппарат → картриджи → график замен |
| Тумблер админ-панели | Тумблер остаётся в UI, роль проверяется на сервере | Видимость на клиенте — не защита. Права проверяются на каждом запросе по белому списку Telegram ID |
| Раздел «Мой фильтр» отсутствовал | Добавлен в MVP | Без него напоминания о картриджах ведут в никуда |
| Собственные темы «Тун/Кун» | Тема берётся из Telegram, переключается вручную | Нативность по умолчанию, брендинг сохраняется |

## 4. Архитектура

### 4.1 Топология развёртывания

Один VPS в Узбекистане. Всё поднимается через `docker compose`.

```
                    Интернет
                       │
                 ┌─────┴──────┐
                 │   nginx    │  TLS (Let's Encrypt), rate-limit,
                 │  :80/:443  │  CSP-заголовки, отдача /media
                 └─────┬──────┘
            ┌──────────┴──────────┐
            │                     │
      ┌─────┴──────┐        ┌─────┴──────┐
      │    web     │        │   worker   │
      │  Next.js   │        │  бот+cron  │
      │   :3000    │        │            │
      └─────┬──────┘        └─────┬──────┘
            └──────────┬──────────┘
                 ┌─────┴──────┐        ┌──────────────┐
                 │ PostgreSQL │        │ /var/app/    │
                 │   :5432    │        │    media     │
                 └─────┬──────┘        └──────────────┘
                       │
                 pg_dump по cron → бэкапы

Внешние сервисы: Telegram Bot API (исходящие + webhook),
                 Kinescope (только iframe в браузере клиента)
```

**Почему `worker` — отдельный контейнер, а не cron внутри Next.js.** Планировщик внутри веб-процесса дублируется при запуске второго инстанса (два напоминания одному клиенту) и умирает при каждом передеплое. Webhook бота требует стабильно живущего процесса, не привязанного к жизненному циклу HTTP-запроса.

**Чего сознательно нет на старте.** Redis и очередь задач (BullMQ) — при нагрузке в сотни клиентов ежедневный cron по таблице справляется, а Redis добавляет отказоустойчивый компонент, который надо администрировать. S3/MinIO — фото лежат на диске, отдаются nginx. Оба решения добавляются позже без переписывания, если появится реальная нагрузка.

### 4.2 Слои приложения

```
маршруты (RSC, route handlers)  ← только приём запроса и рендер
        ↓
      services                  ← вся бизнес-логика
        ↓
    repositories (Prisma)       ← доступ к данным
        ↓
     PostgreSQL
```

Жёсткое правило: бизнес-логика не живёт в React-компонентах и не живёт в route handlers. Расчёт `due_at`, склейка дублей клиента, решение «пора ли слать напоминание» — всё в `services/`, потому что это вызывается из трёх мест (веб, Mini App, worker) и должно вести себя одинаково.

### 4.3 Разделение трёх поверхностей

Одна кодовая база, три группы маршрутов:

| Группа | Путь | Рендеринг | Особенности |
|---|---|---|---|
| Публичный сайт | `/(web)/[locale]/...` | SSR + ISR | SEO, sitemap, hreflang, метаданные, Open Graph |
| Mini App | `/(miniapp)/app/...` | преимущественно клиентский | тема из Telegram, авторизация по `initData`, без индексации |
| Админка | `/(admin)/admin/...` | SSR | проверка роли на сервере при каждом запросе |
| API | `/api/...` | — | заявки, авторизация, webhook бота |

Общими остаются: компоненты каталога и карточки товара, дизайн-токены, `services/`, схема БД. Различаются только оболочка, навигация и способ входа.

### 4.4 Авторизация: два входа, одна сессия

```
Mini App:  WebApp.initData
             → POST /api/auth/telegram
             → проверка HMAC-подписи ботовым токеном
             → проверка auth_date (не старше 24 часов)
             → upsert User по telegram_id
             → JWT в httpOnly + Secure + SameSite cookie

Браузер:   Telegram Login Widget
             → тот же обработчик, та же проверка подписи
             → та же cookie-сессия

Гость:     сессии нет. Доступны каталог и форма заявки по телефону.
```

Роль администратора — поле в `User`. Первичные админы задаются переменной окружения `TELEGRAM_ADMIN_IDS` (bootstrap), дальше выдаются через админку. Каждое админское действие проходит через `requireAdmin()` на сервере. Тумблер админ-панели в интерфейсе — лишь способ показать элементы управления; сам по себе он не даёт никаких прав.

### 4.5 Поток заявки

1. Клиент нажимает «Заказать» → `POST /api/leads`.
2. Валидация схемой (zod), rate-limit по IP и Telegram ID.
3. Нормализация телефона к `+998XXXXXXXXX` → поиск существующего клиента → **склейка дублей**.
4. Запись `Lead(status=new)`. **Ответ клиенту отдаётся здесь** — успех не зависит от Telegram.
5. Асинхронная отправка уведомления в группу менеджеров с inline-кнопкой «Взять в работу», с повторами при сбое.
6. Менеджер ведёт статус в админке: `new → in_work → done | rejected`.

Ключевое: недоступность Telegram API не должна терять заявку. Сначала база, потом уведомление.

### 4.6 Поток напоминаний о замене

Ежедневно в 09:00 по Ташкенту worker:

1. Выбирает `InstalledPart`, где `replaced_at IS NULL` и до `due_at` осталось 30, 7 или 0 дней.
2. Проверяет, что напоминание этого типа ещё не отправлялось — уникальный индекс `(installed_part_id, kind)` гарантирует это на уровне БД, а не логики.
3. Отправляет сообщение с кнопкой «Заказать замену» (сразу создаёт заявку, без прохода по каталогу).
4. Записывает `sent_at`. При ошибке `429` от Telegram — уважает `retry_after` и переносит на следующий проход.

Идемпотентность здесь не опция: повторное напоминание об одном картридже читается клиентом как спам и стоит дороже, чем пропущенное.

### 4.7 Локализация

Публичный сайт: языки в пути — `/uz/...` и `/ru/...`. Отдельные URL нужны для индексации, поэтому переключение языка без смены адреса не подходит. Проставляются `hreflang` и канонические ссылки.

Mini App: язык берётся из `initData.user.language_code`, переключается вручную и запоминается в профиле.

Контент товара хранит оба языка в одной записи (`name_uz` / `name_ru`, блоки описания с языковыми ключами). Отсутствующий перевод падает на узбекский, а не показывает пустоту.

### 4.8 Контент-блоки вместо загрузки HTML

`Product.content_blocks` — массив типизированных объектов в jsonb:

```json
[
  { "type": "heading",   "uz": "...", "ru": "..." },
  { "type": "paragraph", "uz": "...", "ru": "..." },
  { "type": "image",     "src": "/media/...", "alt": {...} },
  { "type": "specs",     "rows": [{ "k": {...}, "v": {...} }] },
  { "type": "video",     "provider": "kinescope", "id": "..." }
]
```

Рендерер сопоставляет `type` с React-компонентом. `dangerouslySetInnerHTML` не используется нигде. Если позже понадобится свободный текст с форматированием, он проходит через `sanitize-html` с белым списком тегов **при сохранении**, а не при выводе.

Это и есть техническое решение конфликта «HTML-презентация против защиты от injection»: свобода вёрстки ограничена набором блоков, зато поверхность атаки нулевая, а страницы выглядят единообразно.

### 4.9 Структура проекта

```

    (miniapp)/app/           Telegram Mini App
    (admin)/admin/           админка и CRM
```

### 4.10 Ключевые решения и их цена

| Решение | Альтернатива | Почему так |
|---|---|---|
| Next.js с SSR | SPA + отдельный API | Публичный каталог должен индексироваться; SPA этого не даёт без отдельного рендера |
| Одна кодовая база на три поверхности | Отдельные проекты для сайта, Mini App и админки | Каталог, модель данных и логика общие; три репозитория означают тройную синхронизацию |
| Worker отдельным контейнером | Cron внутри Next.js | Избегаем дублирования напоминаний и смерти планировщика при передеплое |
| Cron по таблице | Очередь задач с Redis | На старте нагрузка мала, а Redis — лишний компонент для администрирования |
| Файлы на диске + nginx | S3 / MinIO | Хостинг локальный, объём медиа невелик, бэкап делается вместе с сервером |
| jsonb для контент-блоков | Отдельные таблицы блоков | Блоки читаются всегда целиком и никогда не выбираются по отдельности |
| JWT в httpOnly cookie | Сессии в БД | Не требует обращения к БД на каждый запрос; отзыв решается коротким сроком жизни |

## 5. Модель данных (черновик)

```
User            telegram_id, phone, name, lang, role, created_at
Product         kind(filter|cartridge), slug, name_uz, name_ru,
                content_blocks(jsonb), price, images, video_id, is_active
CartridgeSpec   product_id, resource_months
Compatibility   cartridge_id ↔ filter_id
Lead            user_id | phone, product_id, source(miniapp|web),
                status(new|in_work|done|rejected), comment, created_at
Installation    user_id, filter_product_id, installed_at, address, note
InstalledPart   installation_id, cartridge_product_id,
                installed_at, due_at, replaced_at
Notification    installed_part_id, scheduled_at, sent_at, status
AuditLog        admin_id, action, entity, payload, created_at
```

Ключевые следствия:
- Один клиент может иметь **несколько** установок (дом, дача) — модель это допускает.
- Клиент может прийти дважды: из Telegram и с сайта по телефону. Нужна **склейка дублей** по номеру.
- `due_at` считается от `installed_at` + `resource_months` конкретного картриджа, а не от даты заказа.

## 7. Требования безопасности

Исходное требование «защита от injection и других атак» раскрывается так:

- Проверка HMAC-подписи Telegram `initData` на сервере при каждом запросе.
- Роли проверяются на сервере; клиентский флаг админа ничего не решает.
- Все запросы к БД через Prisma (параметризованные), валидация входных данных схемами (zod).
- HTML описаний генерируется системой из блоков и санитизируется — произвольный HTML не принимается.
- Rate-limit на формы заявок и отзывов, защита от спам-ботов на публичной форме.
- CSP-заголовки, HTTPS обязателен, секреты только в переменных окружения.
- Журнал действий администраторов (`AuditLog`).
- Автоматические резервные копии БД с проверкой восстановления.

## 8. Критический путь

Порядок важен: пункты 0 и 1 выполняются **параллельно** с разработкой и чаще всего становятся причиной срыва сроков.

0. **Инфраструктура (на владельце).** ИП или юрлицо → домен → VPS в Узбекистане → Docker + PostgreSQL + бэкапы.
1. **Контент (на владельце).** Минимум 3–5 моделей фильтров: фото, характеристики, цена, описание на двух языках. Список картриджей с ресурсом в месяцах. Видеообзоры.
2. **Проверка риска.** Прототип плеера Kinescope внутри Telegram WebView на реальных iOS и Android. Делается **до** заливки всего видео — если полноэкранный режим не работает, план по видео меняется.
3. Скелет: Next.js + Prisma + PostgreSQL, авторизация (initData + Login Widget), i18n uz/ru.
4. Каталог, карточка товара, заявка, уведомление менеджеру.
5. Админка: товары, редактор блоков, обработка заявок.
6. CRM: клиенты, установки, картриджи, отметка дат.
7. Планировщик напоминаний + экран «Мой фильтр» со шкалами ресурса.
8. Dashboard, баннер, оформление, тёмная и светлая темы.
9. Хардening, бэкапы, нагрузочная проверка, запуск.

## 9. Открытые вопросы

Блокируют детализацию, но не старт разработки.

1. **«Biz mijozlar»** — что это за раздел: «о нас», отзывы клиентов, галерея установок?
2. **«Mahsulotlarini almashtirish»** — какая функция имеется в виду?
3. **Сервис-центр**: колонка «ссылка» в таблице ведёт куда? Зачем «о нас» и «цены» в виде таблицы с поиском?
4. **Отзывы**: публичные или только для владельца? Модерация до публикации?
5. **Kinescope**: аккаунт оплачен? Сколько видео снято?
6. **Объём контента**: сколько моделей фильтров и картриджей на старте?
7. **Сроки и исполнители**: дедлайн, бюджет, кто ведёт разработку.
8. **Квиз подбора** (2-й этап): по каким параметрам и кто даст экспертную логику?
